## 本机（macOS）环境坑，本次新踩到

1. **MySQL 一直在跑，但 `lsof` 看不到**。MySQL 9.0.1 装在 `/usr/local/mysql`，
   data 目录属 `_mysql`；以当前用户 a1 执行 `lsof -iTCP:3306` **列表为空**，
   极易误判成「MySQL 没启动」。判据应改用 `nc -z -v 127.0.0.1 3306`（本次返回 succeeded）
   或直接打后端 API 看有没有数据。
2. **沙箱会隐藏监听端口**。不加 `dangerouslyDisableSandbox` 时 `lsof` 连 8080/5175 都看不到，
   会得出「项目没启动」的错误结论。排查端口必须走非沙箱执行。
3. **本会话 `sudo` 被策略禁用**（`operation not permitted: sudo`）。
   需要系统级权限时只能走
   `osascript -e 'do shell script "..." with administrator privileges'`（会弹 GUI 密码框）。
4. **`mysql.server start` 以 root 运行会失败**：日志报
   `Fatal error: ... run mysqld as root!`，且 `--user=_mysql` 被 `mysqld_safe` 忽略、
   仍以 root 起。若真要手动启动，应绕过 mysqld_safe：
   `sudo -u _mysql nohup /usr/local/mysql/bin/mysqld --datadir=/usr/local/mysql/data --port=3306 ...`
   （本次未走到这一步，因为 MySQL 本来就在跑）
5. **PATH 被 WorkBuddy shim 目录污染**：`head` 会解析到
   `.../cli/vendor/shim/brokered-bin/head` 而报 `command not found`；
   同批次的 `curl`、`ps` 也可能是 `operation not permitted`。
   可靠做法是**全部用绝对路径**：`/usr/bin/head`、`/usr/bin/curl`、`/bin/ps`、`/usr/sbin/lsof`、
   `/bin/ls`、`/usr/bin/nc`。注意 `curl` 必须带 `--noproxy '*'`，否则走系统代理。

- 核心是 `contentJson`，结构：`{version, resources[], steps[]}`，steps **必须正好 3 个且各出现一次**：
  `evidence`（证据阅读）/ `compare`（比较分析）/ `reflection`（反思表达）。
- `LearningTaskService.validateForPublish()` 是发布时的硬校验（创建时不校验，只有 draft→published 才校验）：

## 「赋诗一首」结果页修复（`/compose`，2026-10-05）

用户反馈两点：按钮点了没有播放动画、出来的页面太丑。实为两个**互相独立**的 bug。

### bug 1：动画完全不播放
- 根因：`HanziWriterChar.vue` 的 `charDataLoader` 里调用 `HanziWriter.getCharacterData(char)`，
  但 **hanzi-writer 没有这个静态方法**（3.7.3 里 `getCharacterData` 是实例方法，需先 setCharacter）。
  而且 **hanzi-writer 包本身不含笔画数据**——数据在独立的 `hanzi-writer-data` 包（解包 32MB，本项目未安装）。
  结果每个字的笔画数据都加载失败，`animateCharacter` 无笔画可画，且异常被内部吞掉，**控制台几乎没有报错**。
- 修复：改为按需 `fetch` `https://cdn.jsdelivr.net/npm/hanzi-writer-data@2.0.1/{char}.json`
  （同字内存缓存；jsDelivr 实测可达）。加载失败则降级为静态文字，至少不破版。
  判据：DOM 里 `.char-container svg` 数量 > 0 即表示数据加载成功（实测 56 个 SVG、0 降级）。

### bug 2：排版错乱（字巨大且被拦腰折断）
- 根因：`charSize` 固定 **80px**，一行 12 字需要 12×(80+8)≈1056px，而纸面可用宽度只有约 656px，
  于是 `.poem-line` 的 `flex-wrap: wrap` 把整句折成两段（「渊。」被挤到下一行）。
- 修复：`charSize` 改为按「纸面实测宽度 ÷ 最长行字数」反推，夹在 20–76px；`.poem-line` 改 `nowrap`；
  纸面宽度用 ResizeObserver + window resize 跟踪。
- ⚠️ **踩坑**：`ensurePaperObserver()` 只在 `onMounted` 注册了 resize 监听，**没在 `composePoem` 的
  `nextTick` 后调用**，导致首次渲染时 `paperWidth` 一直是 0 → 退回默认 600 → 字被算成 32px（明显偏小）。
  必须在赋诗成功后显式调用一次。

### 顺带优化（节奏）
- `charDelayMs` 按总字数反推（目标整首 5s，夹在 90–260ms）。原固定 260ms 会让 64 字的诗拖到 15s。
- HanziWriter 参数 `strokeAnimationSpeed` 1→1.6、`delayBetweenStrokes` 200→120，单字约 1.5s。
- 实测 64 字整首书写 **7.5s**（原 10s+），印章延迟 `totalChars × charDelayMs + 0.25s` 正常落下
  （`opacity: 1`）。
- 视觉统一：纸面去掉旧版 `linear-gradient` 改用 `--bg-primary` + `--border-light`；标题改 `--font-display`（楷体）
  + 字距；印章由金色 `#c8a45c` 改朱砂 `--accent`；移除媒体查询里会覆盖自适应字号的 `.char-container{width:60px}`。

### 续：用户反馈「刚开始能看到全部字、像素描一遍」——三个叠加的根因

逐个排查后确认是**三个独立问题叠在一起**，前两个修完仍然"像描红"，第三个才是主因：

1. **`showOutline: true`** → 未写的字先亮出浅灰轮廓（描红底稿）。改 `false`。
2. **笔画数据缓存写错了作用域** → `<script setup>` 里的 `const dataCache = new Map()`
   **是「每个组件实例一份」**！一首诗 60 多个字 → 60 多个并发请求、缓存完全不共享，
   被 jsDelivr 限流，失败的字降级成**印刷体文字**（视觉上就是「有的字不是写出来的，而是印上去的」）。
   **必须放到普通 `<script>` 块做模块级共享**，并加「同字请求去重 + 并发上限 6」。
   判据：`.hanzi-fallback` 数量应为 0；修复前有明显的降级字。
3. **HanziWriter 创建时，笔画的初始显示比例是「完整」的**（不是未写），
   只有 `animateCharacter` 跑起来才把笔画重置到起点。所以**没轮到的字会先整字显形**——
   这才是「刚开始就能看到全部字」的直接原因。
   解法：子组件加 `visible` ref，轮到书写前用 CSS `opacity: 0` 整体遮挡，
   `playAnimation()` 之后同一微任务内置为可见。

## AI 赏析「加载失败」根因与策略调整（2026-10-05 12:15）

用户反馈赏析模块"又加载失败"。**根因不是故障，是内容治理流程**：

2. `KnowledgeRetrievalService.addAnalyses()` / `addAnalysesForPoem()`：**补上发布态过滤**

`compose-score.mjs` 的 water 层：
`cutoff = 0.035 + 0.025·sin(0.37t) + 0.015·sin(1.3t)` —— 两个 LFO 在 **t≈13.3s** 同时落到波谷时
cutoff 变成**负数**，单极点低通翻转为正反馈 → **1 秒内发散到 1e38 → 溢出成 Infinity** →
`peak = NaN/Infinity` → `0.88/peak` 让整条配乐的归一化失效 → **全片配乐实为静音/削顶噪声**。
症状很隐蔽：`volumedetect` 报 `mean_volume: -0.0 dB`（看着像满量程），频谱图后段全黑。
已修：`Math.max(0.004, ...)` 钳住 cutoff，并在归一化前加非有限值告警。
**附带修复**：pad 的相位累加器从 `Float32Array` 改 `Float64Array`
（Float32 在相位 >131k rad 后可表示步长 > 增量，会让声部冻结成直流）。

**教训：代码合成的音频一定要验「分段电平 + 是否削顶」，只听整体响度会被 NaN 归一化骗过。**

- 古琴拨弦整体降为 `PLUCK_GAIN = 0.60`，UI 段由每页 2 个减到 1 个

- 实测：峰值 -1.5～-14.5 dB 有起伏，**全段零削顶**

**不要加 --clean**；只要新帧数 ≥ 旧帧数就会全部覆盖，无残留。

### promo-film 第四轮：peak 文字压背景 + 标注框扭曲（同日 17:3x）

用户第二次反馈「这个也很丑」，并附带指出「后面画线圈出页面原型的圈，画的很扭曲」——两个独立问题：

**1. `peak` 镜头的「一览众山小」被背景吞没**
`act2.js` 里两行诗分别在 `W*0.28` 与 **`W*0.62`**。第二行正好落在**最密的山体**上，
朱红字压在深色岩石上完全读不出来（`mount_tai_anime.jpg` 这张画笔触极密、明暗对比强）。
**左侧 scrim 只覆盖 50% 宽，中间那行根本没被保护到。**
改：两行诗**并排移到左侧**（`W*0.17` / `W*0.275`），`scrim from 'l'` 提到 `size 0.46 / strength 0.80`，
右侧整幅留给山景。
→ **经验：叠加文字的位置必须先看「背景在最密/最深处是否成立」，不能只按左右对称摆。**

**2. `markUI` 的朱红标注框扭曲（真 bug）**
原实现是「逐点行走 + 每段独立的正弦抖动」：
```js
seg2(L + r, T, R - r, T, 40)      // 每条边各自生成点
...
const wob = Math.sin(i * 0.37 + a.x * 0.01) * 1.4
ctx.lineTo(px + wob * 0.5, py + wob)   // x 与 y 同时抖
```
三个问题叠加：**① 每条边都从 `i=0` 重新计数** → 四边抖动相位不连续，角点错位；
**② x、y 同时偏移** → 线条斜向乱抖；**③ 圆角用点阵拼** → 角是折线。
1080p 下表现为波浪形轮廓（细长框尤其明显）。
改：`ctx.roundRect()` 精确圆角 + **用 `setLineDash([easeOut(t)*per, per])` 实现「描线」进度**
（周长 `2(w+h) − 8r + 2πr`），线条从起点到终点完全笔直。
→ **经验：要「手绘感」不能靠给每个采样点加噪声；要么用规整几何 + 描边进度，
要么用一条真正连续的噪声曲线。逐点随机抖动在 1080p 只会显得脏。**

**3. `panel()` 才是「不止一处」的主因（更根本，用户补充指出）**
`kit.js` 的 `panel()` 是一个**只有 5 个点的多边形**，四个角各被一个不同的正弦值推开：
```js
const wob = (i) => Math.sin(seed + i * 1.7) * 2.2
ctx.lineTo(x + wob(1), y); ctx.lineTo(x + w + wob(2), y + wob(3))
ctx.lineTo(x + w, y + h + wob(4)); ctx.lineTo(x + wob(5), y + h)
```
→ 四条边互不平行、每个角都是歪的。它用于 **`ui-source`（一次画三个溯源 chip）**、
`ui-ai`（对话面板）、`ui-learn`（示例习作框）——所以用户说「不止一处」完全正确。
改为 `ctx.roundRect()` + 保留原有柔和阴影。

**⚠️ 反模式总结（本轮修了三处，全是同一个错）**：
`markUI` / `panel` / `annotateCircle` 都试图用**逐点采样 + 正弦噪声**去画一个本该规整的几何形状
（矩形/圆），结果在 1080p 下一律表现为「边不直、角错位、像手抖」。
**正确做法**：用 `roundRect()` / `arc()` 画精确几何，需要手绘感时再加**连续的**低频扰动，
或改用描边进度（`setLineDash`）、笔触渐变等手法。
`annotateCircle` 目前是死代码（`act2.js` 只 import 未调用），若日后启用需先修。
