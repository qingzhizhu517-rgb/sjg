## 数据库素材缺口审计（同日）

### 数据库连接方式
- 本机 MySQL 在跑，**客户端在 `/d/app/mysql/install/bin/mysql.exe`**（不在 PATH）。
- 连接参数取自环境变量：`MYSQL_HOST` / `MYSQL_PORT` / `MYSQL_USER` / `MYSQL_PASSWORD`
  （`application.yml` 读的是 `SPRING_DATASOURCE_*` / `DB_PASSWORD`，同一套库）。
- ⚠️ **有效库是 `sjg01`，不是 `sjg`**。两者并存：`sjg` 是近乎空的旧测试库
  （诗 8 / 诗人 6 / 景点 10），`sjg01` 才是生产副本
  （诗 203 / 诗人 129 / 景点 71 / 文化条目 63）。
- 具体实例数别信 `information_schema.TABLE_ROWS`（InnoDB 估算值），要用 `COUNT(*)`。

### 媒体字段的两种存储形态（排查时容易漏）
- **OSS 外链**：存成 **JSON 数组字符串**，如
  `["https://shandong-lit-landscape.oss-cn-beijing.aliyuncs.com/spots/xx.jpg", ...]`
- **本地资产**：存相对路径，如 `/images/spots/baotu_spring.jpg`（落在 `display-v2/public/`）
- 因此「字段非空」不等于「素材存在」：`[]` 空数组等同于缺失，必须解析后判断。

### ⚠️ 两个必须记住的坑

**1. mysql 客户端在 Windows 下默认输出本地字符集（GBK），不是 UTF-8。**
导出中文数据必须加 `--default-character-set=utf8mb4`，否则：
```bash
mysql ... -N -B -e "SELECT ..." > out.tsv      # ❌ GBK
mysql ... --default-character-set=utf8mb4 ... # ✅ UTF-8
```
我第一版导出的 TSV 是 GBK，被 Node 按 UTF-8 读成乱码，
生成的 CSV 里记录名全是 `ǧ��ɽ`；更隐蔽的是——**URL 路径也因此变成乱码，
导致对 OSS 发请求拿到的全是 404**，差点把「编码错误」误判成「素材缺失 186 条」。
判别方法：读出来若含 `\uFFFD`（替换字符）就是编码错了。

**2. 访问 OSS 必须绕过本机代理。**
本机系统代理（`https_proxy=http://127.0.0.1:<port>`）对 OSS 域名 TLS 握手失败，
`curl` 走代理返回 `000`；加 `--noproxy '*'` 直连则正常 `206`。
另外本机 DNS 时而是 fake-ip（`198.18.0.x`）时而解析真实 IP，会随代理配置变化——
**先探测再下结论**，不要凭一次失败就判定素材缺失。
