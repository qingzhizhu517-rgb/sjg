# 内容来源与审核工作台设计

## 背景

SJG 已有来源文献、实体关联和内容审核的数据模型与后端接口，但管理员缺少一条可操作的内容治理路径。首批真实“一城一课”需要先录来源、再关联实体、最后审核发布，因此治理能力必须同时具备数据正确性校验和管理端操作入口。

## 目标与边界

目标是提供一个统一的 `/content-governance` 管理工作台，完成来源登记、实体关联查询和审核状态流转。第一版不引入批量导入、自动抓取、全文 OCR 或复杂权限矩阵；真实实体和来源仍由管理员依据外部材料录入。

## 交互结构

页面包含三个标签页：

1. **来源文献**：分页搜索来源，创建或编辑来源类型、标题、作者/机构、年份、标识、URL、规范引用和版权说明。
2. **实体关联**：选择实体类型和正整数 ID，选择已登记来源，填写页码/段落、原文摘录和关联说明；保存后显示该实体的全部来源摘要。
3. **审核队列**：按实体类型和审核状态筛选，按照 `needs_review -> approved -> published -> archived` 推进状态，并保留审核备注。

移动端使用单列表单和可横向滚动表格，长标题、来源 URL 和原文摘录不遮挡操作控件。

## 后端契约

- `PUT /api/admin/source-documents/{id}`：编辑来源，必须存在且标题非空。
- `GET /api/admin/source-links/{entityType}/{entityId}`：返回 `SourceSummary[]`，包含来源信息、定位、摘录、备注和实体审核状态。
- `POST /api/admin/source-links`：创建关联；校验来源存在、实体类型受支持、业务实体真实存在，并拒绝相同实体/来源/定位的重复关联。
- 保留现有 `GET/POST /source-documents` 和审核流转接口，响应继续使用 `{ code, message, data }`。

业务实体校验覆盖 `dynasty`、`poet`、`poem`、`scenic_spot`、`event`、`cultural_item` 和 `poem_analysis`。审核状态校验仍由任务发布和公开检索服务负责，避免管理端关联阶段阻塞来源补录。

## 数据流与错误处理

管理员提交表单后，前端先做必填校验，后端再执行存在性和唯一性校验。后端以明确的中文错误信息返回实体类型、实体 ID 或来源 ID；前端通过统一 API 拦截器展示错误。取消审核备注输入不应产生错误提示。

## 验收与测试

- 服务层测试覆盖：实体不存在、重复关联、来源编辑和已有来源摘要。
- 管理端构建必须通过，路由和侧栏能进入工作台。
- 全量后端测试、三个前端构建、展示端单测、迁移检查和 `git diff --check` 必须通过。
- 没有业务数据库时只验证结构和接口契约，不写入占位实体或来源。
