# 山东微缩景观沙盘：参考图分析与构建方案

**状态：设计方案，尚未实施。** 本轮仅分析用户提供的参考图并编制方案，不修改运行时代码。此方案调整上一轮的视觉方向；已实现的相机、编辑与草稿功能继续保留。

**Goal:** 将 `/river-sandbox` 从简化绿地浮雕提升为具有展馆质感、可自由观察和编辑的山东微缩景观。

**Architecture:** 复用 Vue/Three.js 交互门面，将视觉场景拆成地台、地表、海河、植被城镇、标记与照明；地理底图、艺术表现和用户编辑分层。优先建立整体画面及一个精细样板区，再扩展全省，逐层测量成本。

**Tech Stack:** 当前仓库 Three.js 0.184 系列、Vue 3、Vite；沿用 WebGLRenderer。离线处理地理数据、制作网格和压缩资产，浏览器负责分级加载、交互与渲染。此阶段不以升级引擎或引入新地图平台作为前提。

## 1. 对参考图的判断

这是展馆式微缩景观的视觉语言：山东主体突出于低对比度的周边底图，东侧海水形成冷色空间，金色轮廓、河岸和城市竖牌建立导览秩序。图片能说明目标观感，但无法据此判断它是否为实时画面、使用何种引擎或真实几何规模，也无法恢复背面与被遮挡区域。

### 决定相似感的八个构成

| 构成 | 图中可见特征 | 应复刻的结果 | 实现策略 |
|---|---|---|---|
| 构图 | 斜俯视、主体横跨画面、背景压暗 | 第一眼看到山东、河流和山脉 | 固定一个主展示机位，省域完整进入画幅；相机初始俯角35–50°作为试调范围，并非从图反求的参数 |
| 展台 | 省域有厚度，周围仍有地理背景 | 有真实物体摆在桌上的尺度感 | 深色矩形底座、浅层周边地形、抬高的省域及岩土侧壁；展馆仅做简洁框景 |
| 山体 | 多条山脊、裸岩断面、植被分布 | 远看有轮廓，近看有岩石细节 | 高程数据决定大形，局部艺术夸张，坡度控制岩石/林地材质，少量精选岩块增强轮廓 |
| 平原 | 黄绿田块、道路水渠、稀疏树带 | 平坦地区也有丰富结构 | 平原遮罩内生成连续田块纹理；道路和树带沿结构组织，避免全省均匀撒点 |
| 城镇 | 建筑成群，高低有变化 | 识别城市聚落而非孤立方块 | 少量建筑原型按街区实例化；中心密、边缘疏；主要城市保留少量特征模型 |
| 海与河 | 深蓝海水、青色浅滩、亮蓝河流 | 冷暖对比与清楚的海陆关系 | 海面、近岸颜色带、河水与金色岸线分层；动态法线与缓慢流动；蓝色黄河定义为艺术导览色 |
| 边界与标记 | 金色细边、棕金竖牌、短光柱 | 主体突出、城市清晰 | 合并省域外边界，内部行政边界减弱；发光线带有实体内芯，局部辉光；九城竖排中文 |
| 光影与镜头 | 暖光、冷海、细小接触阴影、前后景虚化 | 微缩摄影与展陈质感 | 一盏主光、环境反射、静态烘焙细节阴影；景深仅用于展示镜头，交互时淡出 |

建议色彩：海水深蓝、浅滩青蓝、植被橄榄绿、农田土黄、裸岩灰褐、导览暖金、牌面深棕。具体值在真实渲染里按曝光一起调，不把截图取色当材质的最终参数。

### 不照搬的部分

- 参考图属于艺术表现；山峰高度、建筑密度、河宽、近岸色带均不能直接视为实测值。
- 河流与城市必须从同一地理基准投影，不能为了串联九城而移动河道或城市。必要时移动标签牌面，用引线保留真实锚点。
- 全站继续使用已有纸面导航与文字系统；仅沙盘视口内部采用展馆微缩景观。页面主视口可全宽展开，统计与编辑面板按需打开。
- 不使用整幅参考图贴在平面上冒充三维。相机可以旋转，所以山体、海岸、底座必须具备实际空间结构。

## 2. 当前实现的差距与复用边界

本轮直接读取当前代码核对：

- `scene.js` 已有精确行政多边形几何、侧壁、城市锚点和材质，但地表主要由高度渐变着色，无田块、路网、城市群、海面及展台环境。所有行政 rings 当前共用边线；省域金边需要先合并市界提取外轮廓。
- `geography.js` 的地形由三处山体中心与三角函数合成；`core.js` 的基准高度实际采样至112格网。即使增加渲染三角形，也不会凭空获得山脊和地表细节。
- `editor.js` 每次笔刷刷新整块地形；`sync()` 会重建用户物件。扩展到大规模植被城镇后必须保持装饰场景与编辑物件分离。
- `useThreeSandbox.js` 负责相机、飞行、拾取、生命周期和帧循环，可继续使用。城市拾取当前依赖单个 `world.land`，分块地形需要改为碰撞网格集合。
- 草稿目前为 `schemaVersion:1`，保存世界坐标与格网增量。更换投影或基准高程后不能直接把旧地形增量套在新地表上。

应保留：旋转缩放平移、城市选择、手势取消、撤销重做、导入校验、本地保存、后台暂停、上下文恢复。此次主工作量在场景资产、地表材质、构图与渲染，不再重复堆叠操作按钮。

## 3. 建议技术路线

### 3.1 数据与地形

1. 核验行政边界、河流、城市、高程的坐标基准、范围和来源；现有边界的 CRS 不能只凭外观认定。
2. 统一到一种已记录的地理基准后离线投影，输出稳定的 `projectionId` 与场景范围。
3. 高程优先评估 Copernicus GLO-30/90。它是包含植被/建筑的 DSM，不等同裸地 DTM；需平滑、降采样、检查水域并按许可保留来源。真实数据缺失时保留明确标注的程序化预览。
4. 将全省切成地形块，离线生成粗/中/细网格、坡度/土地分类遮罩、法线贴图。不能把原始30米全省数据直接展开成浏览器网格。
5. 高度基准与视觉夸张参数分开；先用一个可调全局夸张系数，再决定是否需要泰山区域的局部艺术加强。主山峰位置不漂移。
6. `terrain.sample(x,z)` 作为渲染、锚点、碰撞和物件贴地的统一采样入口；每块 LOD 用同一高度源，处理边缘裂缝。
7. 用户笔刷写入独立增量层，受影响的地形块局部刷新，连带更新其树木/建筑高度。海岸、河道等受保护区域保持明确边界。

### 3.2 地表与模型

- 田块：主要写入地表颜色/粗糙度/法线图集，重要田埂可用少量几何；不用一个田块一个 Mesh 的方式铺全省。
- 山体：大轮廓交给地形，岩层交给材质；局部悬崖、峰顶使用少量岩块模型。避免用密集随机锥体代替山脉。
- 森林：按坡度、高度与土地遮罩布点，按空间块分组实例化；远处降为低面数树冠或地表纹理。
- 城镇：一组住宅/楼房/屋顶原型，按真实城市锚点生成示意街区；若无真实建筑 footprint，明确标为示意聚落。
- 地标：精选少量具有齐鲁辨识度的模型，记录来源、许可与是否为历史复原。没有可靠依据时不声称复原古建筑原貌。
- 美术资产可以由本地模型制作流程生成并导出 GLB，Web 端处理 KTX2 压缩纹理及兼容回退；不把复杂材质节点原样搬到浏览器。

### 3.3 水体、边界、灯光

- 海面使用简洁平面与两层滚动法线。近岸色带来自岸线距离，属于视觉水深提示；没有海底数据就不标称真实水深。
- 河流从已核验线数据生成变宽 ribbon，渲染高度与地形统一；河岸金线和河水分别绘制。避免全程高饱和发光，把细节洗成白色。
- 省界用带实际宽度的带状几何或适配屏幕宽度的线，避免依赖普通 WebGL lineWidth 获得粗描边。外边界明亮，内部边界细暗。
- 光照采用固定暖色主光、低强度环境反射和接触阴影。大多数静态建筑/树木不逐帧更新实时阴影。
- 默认不启用昂贵全屏反射。辉光限定省界、河岸和标记；半分辨率起步。展示镜头可使用轻微景深，交互/编辑/移动端关闭。
- 后处理必须统一色彩与输出路径，不能发生重复色调映射；所有档位都检查材质颜色、透明水面与标签清晰度。

### 3.4 导览与编辑

- 默认“观览”：画面占主体，工具收为一排；城市点开资料侧栏，编辑面板按需展开。
- 竖牌采用 HTML/SVG 或小型纹理牌面；保留可键盘触达的真实 DOM 控件。地图内牌面与地面锚点分离，视角变化时进行遮挡和避让。
- 模型装饰层以空间块批量绘制，不进入500个用户物件上限；用户新增物件保留独立 ID、变换与撤销记录。
- 批量实例被选中时用 `instanceId → 稳定实体ID` 映射；编辑结束回写实例变换与包围体。不可因批次排序导致选错对象。
- 草稿升级需增加 `baseTerrainVersion`、`projectionId`、格网范围与版本。V1 数据原样保留；基准不兼容时提供明确提示和保留旧场景的读取路径，不静默丢失或错位迁移。

## 4. 资产清单与取得方式

| 资产 | 必要性 | 获取/生成方式 | 验收 |
|---|---|---|---|
| 省域外轮廓、城市边界 | 必须 | 现有文件核验后合并外轮廓 | 市界不会变成粗发光裂缝，岛屿与孔洞保留 |
| 河道、九城锚点 | 必须 | 复用已记录来源的坐标并核验投影 | 不为了构图移动真实落点 |
| 高程块与采样数据 | 核心 | 合法高程数据离线裁切、过滤、减面 | 山脉结构可信，三档无明显接缝 |
| 农田/岩石/森林材质 | 核心 | 程序化生成与有许可材质制作 | 无大面积重复棋盘感，放大后保持尺度 |
| 建筑/树木/岩石原型 | 核心 | 自制少量可复用原型与压缩 GLB | 远中近三级有差异，轮廓不突变 |
| 特色地标 | 第二阶段 | 自制或有许可的模型 | 有来源说明，历史示意与真实复原区分 |
| 环境照明 | 核心 | 简化展厅模型或有许可环境贴图 | 水面/侧壁有合理反射，不压暗可读区域 |

可首先程序化完成：展台、金边、水面、田块、简化建筑群、基础树木和竖牌。接近参考图的山岩质感、森林层次与地标辨识度需要认真制作高程/材质/模型；单靠调灯光无法补齐。

## 5. 按画面结果分阶段构建

- [ ] **A — 整体样板。** 固定参考机位，完成山东主形、桌面底座、周边低对比底图、海面、金色外边界、九城竖牌和昼间暖光；用简单地表验证构图。输出桌面全景、窄屏全景和反向旋转截图。验收重点：全省轮廓完整、海陆关系清楚、主体占画面约三分之二到四分之三、面板不遮主体。
- [ ] **B — 一个精细样板区。** 先做“济南—泰安—黄河沿线”，一次包含平原田块、城市群、山脉、河水和标牌。输出全景、中景、近景、连续旋转片段；确认不依赖固定镜头遮丑，再铺开全省。
- [ ] **C — 全省扩展。** 加入鲁西北田块、鲁中山脉和胶东海岸的差异，按空间块加载装饰实例，补齐合法资产清单。检查重复纹理、浮空建筑、水体穿模和相机反向视角。
- [ ] **D — 交互融合。** 接回城市资料、选中、拖拽、笔刷、撤销与草稿迁移；编辑一块地形后立即验证建筑贴地、河岸保护和撤销恢复。
- [ ] **E — 光效与性能收尾。** 在前述画面已达标后逐项加入辉光、接触阴影和展示景深；逐项记录性能代价，完成低档降级、后台暂停和连续交互压测。

每一阶段用真实浏览器截图/连续录屏对照参考图验收；构建通过和单测通过不能替代外观验收。本方案不承诺从单幅图片像素级还原完整三维场景。

## 6. 性能方案与测量口径

上一轮记录：开发浏览器精细+细雨60秒约29.13 FPS，混入交互及无障碍扫描。它不是可归因的 GPU 基准，可能受浏览器节拍、系统电源、屏幕刷新、渲染或主线程成本影响。

先执行独立基线：固定设备、窗口、DPR、生产构建和主机位；分别测空场景、静态地形、阴影、粒子、标签和后处理。记录 RAF P50/P95、主线程长任务、draw calls、三角形、纹理尺寸；设备支持时增加 GPU timer query 并处理 disjoint。每组预热后测60秒，轨迹保持一致。

以下是**起始预算，尚未实测达成**：

| 项目 | 均衡桌面 | 省电/移动 |
|---|---|---|
| 帧率目标 | 60 FPS，依据设备降级 | 稳定30 FPS优先 |
| DPR上限 | 1.5 | 1.0–1.25 |
| 可见三角形 | 约50万以内起步 | 约15万以内起步 |
| 全帧 draw calls | 约150以内起步，含阴影/后处理各pass | 约80以内起步 |
| 阴影 | 一盏主光，1024–2048，静态缓存 | 512–1024或烘焙替代 |
| 辉光/景深 | 半分辨率局部辉光；景深仅展示 | 默认关闭 |
| 反射 | 环境贴图与近似水面 | 简化环境色与法线 |
| 资源传输 | 首批可交互资源压缩后目标≤8MB | 优先低LOD资源 |

实例化按空间块拆分，保证视锥裁剪有效；不会把全省树木装入一个无法局部剔除的大批次。纹理按实际显存成本控制，下载体积小不等于解码占用小。自动降级要有观察窗口和恢复滞回，避免画质反复跳动。关闭动态且相机/编辑/加载均静止时改为按需渲染。

## 8. 已核验的技术参考

- Three.js 实例化：<https://threejs.org/docs/pages/InstancedMesh.html>。适合相同几何与材质、不同变换的重复对象；变换后须更新实例缓冲及相关包围体。
- Three.js LOD：<https://threejs.org/docs/pages/LOD.html>。按距离切换对象；自定义分块实例系统仍需要自己的批次管理，不能假设加入一个 LOD 就自动管理所有实例。
- Three.js 选择性辉光示例：<https://threejs.org/examples/webgl_postprocessing_unreal_bloom_selective.html>。仅作机制参考，实际按仓库锁定版本验证，需计算额外pass成本。
- Copernicus DEM 产品页：<https://dataspace.copernicus.eu/explore-data/data-collections/copernicus-contributing-missions/collections-description/COP-DEM>。GLO-30/90为全球DSM，使用需遵循来源声明。
